# summer4 0.2.0a7

**Tag:** `v0.2.0a7` · **Date:** 2026-10-29 · **Status:** alpha

Three changes that let `monash-emu/summer4template` express summer3's example
model directly. It is the summer4 that template pins.

- **Homogeneous mixing over the whole population** needs no extra property.
- **Calibration targets can name a transformed output**, such as a 7-day rolling
  sum of infections.
- **`sum_by`** replaces `total()` and `sum_over()`, which read wrongly. The old
  spellings still work, with a deprecation warning.

## Install

```toml
[pypi-dependencies]
summer4 = { git = "https://github.com/monash-emu/summer4.git", tag = "v0.2.0a7", extras = ["calibration", "pandas", "frames"] }
```

## Whole-population force of infection

`ForceOfInfection`'s `group_by` is now optional, and leaving it out is the
default. The whole population is then one group, so the frequency force of
infection is `contact_rate * I_total / N_total` however the compartments are
stratified. That is summer2's default.

```python
foi = ForceOfInfection("foi", infectious=state["I"], contact_rate=Param("beta"))
```

Before, the same model needed a one-trait property (`Property("pop", ("all",))`)
stratified onto every compartment, a `[[1.0]]` mixing matrix, and the force of
infection grouped by that property. Both give identical trajectories; the new
spelling adds no compartment-label suffix.

- The flow rate is a scalar; the captured force of infection saves as a
  `("time",)` series.
- `kind`, `denominator`, `exponent`, selector-pair `infectiousness` and both
  `normalize_infectiousness` modes work with one group. A custom `kind`
  callable receives `GroupedRate` values with `properties=()`.
- `mixing=` or a trait-keyed `infectiousness` mapping without `group_by` raises.

`group_by=age` without a `mixing=` matrix is **not** homogeneous mixing: each age
group then catches infection only from itself. Acceptance notebook
`examples/notebooks/30-foi-whole-population.ipynb` shows the difference.

Closes the whole-population half of composability finding `CX15` (PR #65). Pages
written before this release still teach the dummy property;
`futureplans/foi-dummy-pop-docs-migration.md` tracks moving them.

## Calibration targets on transformed outputs

A target can be keyed to an output of `BayesianModel(..., outputs=)`:

```python
outputs["weekly_infections"] = FlowMass("infection").sum_by().rolling(7, how="sum")
target = Target.from_series("weekly_infections", observed, epoch, likelihood=Poisson("sum"))
bm = BayesianModel(model, {}, priors, TargetSet((target,)), outputs=outputs, run_kwargs=run_kwargs)
```

Before, such a target raised `KeyError`. Giving it the output's quantity instead
saved that quantity only at the observation times, so a time-window output
(`rolling`, `cumulative`) was computed over the observations rather than the
run, with no error. Outputs now save on the run's own grid and an output target
is read from the evaluated output. `BayesianModel.save_plan` shows the plan;
`posterior_runs` uses the same one. `rolling(n)` counts saved points, so it is a
7-day window on a daily grid.

Acceptance notebook `examples/notebooks/31-calibration-output-targets.ipynb`
(PR #67).

## `sum_by`: summing across strata

`sum_by` is named for what it keeps, as pandas' `groupby(...).sum()`:

| Before | Now | Keeps |
|---|---|---|
| `.total()` | `.sum_by()` | time |
| `.sum_over(age)` | `.sum_by(age)` | time, one value per age |
| — | `.sum_by(age, strain)` | time, one value per (age, strain) pair |
| `FlowRef(f).sum()` | `FlowRef(f).sum_by()` | — |
| `Compartments(sum_over=age)` | `Compartments(group_by=age)` | — |

It works on `Output`, output expressions, save specs, `PropertyData` and
`FlowRef`. Time is never summed by `sum_by`; a single number over time comes
from `integrate`, `cumulative`, `rolling` or `at`.

Acceptance notebook `examples/notebooks/32-sum-by.ipynb` (PR #68).

## Compatibility

- Whole-population FOI is additive: code that passes `group_by=` behaves
  exactly as in 0.2.0a6.
- Plain-leaf outputs targeted by name now save on the run's grid rather than
  only at the observation times. Scores are unchanged when the observation
  times lie on that grid.
- `total()`, `sum_over()`, `FlowRef.sum()` and `sum_over=` still work and return
  the same results, with a `DeprecationWarning` naming the replacement. They
  will be removed in a later release.
