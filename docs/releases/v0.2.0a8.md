# summer4 0.2.0a8

**Tag:** `v0.2.0a8` · **Date:** 2026-10-30 · **Status:** alpha

- **float64 by default.** Importing summer4 turns on JAX's 64-bit mode, as summer2 did.
- **Cumulative counts from rates.** `cumulative_integral()` integrates a rate over time;
  `cumsum()` is the plain running sum. `cumulative()` is deprecated.
- **Time-free outputs combine with series**, `at()` is lazy, and `array()`, `scalar()`
  and `with_values()` move between outputs and plain arrays without `defer`.

It is the summer4 that `monash-emu/summer4template` pins.

## float64 by default

Before this release everything ran in JAX's default float32, which keeps about seven
significant figures: a compartment of 100 million can only move in steps of 8 people,
so small flows into large compartments were lost and populations drifted. Importing
summer4 now turns on `jax_enable_x64`, unless the `JAX_ENABLE_X64` environment variable
is set.

For float32, set `JAX_ENABLE_X64=0` before starting Python, or turn the flag off after
importing summer4 and before compiling:

```python
import summer4
import jax

jax.config.update("jax_enable_x64", False)
```

The flag is process-wide, so it applies to all JAX code in the process (composability
finding `CX41`; a per-model `compile(dtype=)` is in `futureplans/per-model-dtype.md`).
Acceptance notebook `examples/notebooks/35-float64-default.ipynb` (PR #69).

## Cumulative counts: `cumsum()` and `cumulative_integral()`

A flow output is a rate: people per unit time at each save. `cumulative()` was a running
sum of the saved values, which is a count only when saves are one time unit apart, and
even then off by one sample.

| Use | For |
|---|---|
| `cumulative_integral(start=, end=)` | a running trapezoid integral of a rate: cumulative people, whatever the save spacing; 0 at `start` |
| `cumsum(start=, end=)` | a running sum of amounts per interval (`integrate_intervals()` output, `midpoint()` series, counts) |

Both work on `Output`, output expressions and save specs. `cumulative()` still returns
what it did, with a `DeprecationWarning` naming both. Acceptance notebook
`examples/notebooks/34-cumulative-integral.ipynb` (PR #70).

## Time-free outputs and plain arrays

An output reduced over time (`integrate()`, `at(t)`) has no `time` dim and now combines
with a series by broadcasting over time:

```python
share = rate / rate.integrate()           # share of the whole-period total at each time
change = prevalence - prevalence.at(30.0)  # change since day 30
```

Before, both raised *Output time axes differ*. `at(when)` also works lazily in an
`OutputSet`. `array()` and `scalar()` give an output's values as a plain (traced) array,
eagerly or lazily, to combine with numbers, `Param` expressions and NumPy ufuncs.
`with_values(arr)` turns an array back into an output with the original times and dims,
for plotting or as a calibration target. Acceptance notebook
`examples/notebooks/33-time-free-outputs.ipynb` (PR #71; `CX39`, `CX40`).

## Compatibility

- Results change slightly: runs are float64 instead of float32. Code that relied on
  float32 (tolerances, memory, GPU backends without float64) can opt out as above.
- `cumulative()` warns; nothing is removed.
- The NUTS tuning gate (notebook 29) now claims the Laplace start cuts dense warm-up by
  at least a third rather than half, because in float64 the dense warm-up from the
  identity sometimes adapts quickly.
